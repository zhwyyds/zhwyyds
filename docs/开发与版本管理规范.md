## 二、分支与协作模型（双主干）

```
┌─────────────────────┐     PR + CI 门禁      ┌─────────────────────┐
│  dev 开发主干        │ ───────────────────►  │  main 稳定主干       │
│  所有开发、验证在这   │  CI 全绿才可合入       │  只进验证通过的功能    │
└─────────────────────┘                       └─────────────────────┘
```

| 规则 | 说明 |
|---|---|
| 长期分支 | 只有 `dev`（开发）和 `main`（稳定）两个 |
| 短期分支 | `feature/xxx`、`fix/xxx`、`docs/xxx`，用完即删 |
| 开发流程 | feature 分支 → dev 验证 → PR 合入 dev → 稳定后 PR dev→main |
| main 保护 | 禁止直推 + force push 被拒（GH006）+ CI 门禁 |
| 环境 | dev 分支 = 测试环境；main 分支 = 生产环境（发布时） |

## 三、版本管理（语义化版本 SemVer）

### 3.1 版本号规则

```
vX.Y.Z
│ │ └─ Z 修订号：修复 bug（兼容）
│ └─── Y 次版本号：新功能（兼容）
└───── X 主版本号：不兼容的大变更
```

### 3.2 阶段规则

| 阶段 | 版本范围 | 规则 |
|---|---|---|
| 初始期（现在） | v0.x.y | 功能快速迭代，每次发版 +Y（v0.1.0 → v0.2.0 → v0.3.0） |
| 稳定期 | v1.0.0+ | 新功能 +Y，修 bug +Z，大变更 +X |

### 3.3 版本来源（唯一真源）

- 版本号统一维护在 `pyproject.toml` 的 `version` 字段
- 代码内 `data_governance/__init__.py` 的 `__version__` 必须与 pyproject 一致（测试断言 `test_smoke.py` 校验）
- 发版时打 git tag（`vX.Y.Z`），tag 与代码版本号必须一致

| v0.2.0 | （待发） | 双主干 + 模块文档 + 环境标识 |

## 四、环境隔离（测试 / 生产）

### 4.1 概念

| | 测试环境（dev） | 生产环境（main） |
|---|---|---|
| 代码来源 | dev 分支 | main 分支（打 tag 后） |
| 运行位置 | 本地 8080/8765 | 未来服务器 |
| 数据 | 测试数据，可随意造 | 真实业务数据，备份保护 |
| 页面徽标 | dev 蓝 · vX.Y.Z | main 绿 · vX.Y.Z |
| 用途 | 开发、验证 | 日常真实使用 |

### 4.2 当前实现（已启用）

- **环境标识**：页面顶栏徽标（H26）——`/api/meta` 实时读 git 分支，dev 蓝 / main 绿 / 未连接红
- **数据位置**：当前测试/生产共用 `metrics/`、`reviews/` 目录（见 §4.3 待改造项）

### 4.3 数据目录隔离（待改造，方案已定）

**目标**：测试数据与生产数据物理分离，切换环境不污染数据。

**方案**：引入 `DATA_GOV_BASE_DIR` 环境变量 + 目录分层：

```
data_go/
├── dev-data/        # 测试环境数据（dev 分支默认）
│   ├── metrics/  reviews/  roots/  config/
└── prod-data/       # 生产环境数据（main 分支部署时）
    ├── metrics/  reviews/  roots/  config/
```

- 启动时 `DATA_GOV_BASE_DIR=dev-data`（测试）或 `=prod-data`（生产）
- 代码按 `base_dir` 参数解析路径（已支持 `--base-dir`，H 系列已标准化）
- **改造范围**：CLI 默认值 + `.env` 配置 + 运维手册启动命令

**验收标准**：同一份代码，切 env 变量后数据目录不同、页面徽标不同、互不污染。

## 五、发版流程（每次发布执行）

```
□ 1. 开发完成：dev 分支所有模块文档「任务清单」全部 ✅
□ 2. 全量验证：pytest 172 全绿 / ruff / mypy / JS 语法
□ 3. 真实环境验收：Playwright pageerror=0 / console error=0 / 4xx=0 + 截图
□ 4. 数据检查：测试数据（_N 指标 / mock 评审）已清理，不混入正式数据
□ 5. 版本号更新：pyproject version +Y（新功能）或 +Z（修复）→ __version__ 同步
□ 6. 打 tag：git tag vX.Y.Z && git push origin vX.Y.Z
□ 7. PR dev → main：CI 全绿 → 合并 → main 成为新基线
□ 8. 更新文档：docs/README.md 版本历史 + 模块索引状态
```

## 六、变更留痕（所有变更必须记录）

| 类型 | 记录位置 |
|---|---|
| 开发过程 | `docs/modules/<module>.md`（任务清单 + 测试结果） |
| 问题复盘 | `development-playbook.md`（§1 问题明细表） |
| 每日工作 | `.workbuddy/memory/YYYY-MM-DD.md` |
| 代码变更 | git commit（规范信息：前缀 + 描述 + 根因 + 验证） |
| 发版历史 | 本文档 §3.4 版本历史表 |

**铁律：没有记录的变更视为未完成**——任何功能改动必须能在 `docs/modules/` 找到对应任务清单与测试结果，否则不算完成。
