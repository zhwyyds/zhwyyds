# 模块开发文档规范

> 本文档定义 data_go 项目**模块化开发**的标准流程与存档要求。
> **每个模块的开发必须包含：任务清单（开发前） + 测试结果（开发后），并存档到 `docs/modules/`。**
> 配套规范见 `development-playbook.md` §4.10。

---

## 一、模块划分

按前端功能页面划分（每个页面 = 一个模块），当前共 13 个模块：

| 模块 | 页面 | 职责 |
|---|---|---|
| dashboard | 治理总览 | 数据看板、统计卡片 |
| metrics | 指标库 | 指标卡片、详情抽屉 |
| metric-mgmt | 指标管理 | 指标 CRUD、批量操作、分页 |
| roots | 词根库 | 词根 CRUD、AI 生成 |
| batch-gen | 批量生成 | 原子指标+修饰词 → 派生指标 |
| review | 模型评审 | 多模型评审、结果展示 |
| scoring | 评分中心 | 指标评分 |
| acceptance | 验收 | 验收报告、维度评分 |
| caliber | 口径治理 | 口径冲突、待核查 |
| caliber-check | 口径核查 | 口径核对 |
| lineage | 血缘管理 | 指标血缘图 |
| table-lineage | 表血缘 | 表级血缘、字段映射 |
| settings | 系统设置 | 模型/修饰词/评审记录管理 |

> 后端按 `src/data_governance/` 子包划分（api / io / llm / pipeline / scoring / acceptance / caliber / compare / parsing / services / schemas / prompts）。

## 二、模块开发流程（标准动作）

```
1. 建任务清单  → docs/modules/<module>.md 的「任务清单」区
2. 开发（在 dev 分支 + feature/<module> 子分支）
3. 逐项完成清单，勾选状态
4. 全量测试 + 真实环境验收
5. 填「测试结果」区：命令输出 + 截图 + 结论
6. 提交 dev → PR 合入 main（验证通过才可合入）
7. 更新 docs/modules/README.md 索引状态
```

## 三、任务清单模板

```markdown
## 任务清单

| # | 任务 | 状态 | 验收标准 |
|---|---|---|---|
| 1 | 描述要做什么 | ☐ 待办 | 如何判定完成 |
| 2 | ... | ☐ 待办 | ... |

状态：☐ 待办 → 🚧 进行中 → ✅ 完成
```

要求：
- 开发前先写清单（列清楚每件事 + 验收标准）
- 每完成一项立即把 ☐ 改为 ✅，不让清单过期
- 验收标准必须可验证（不是"实现好"而是"点 X 出现 Y / 测试通过"）

## 四、测试结果模板

```markdown
## 测试结果

- 测试时间：YYYY-MM-DD HH:MM
- 测试分支：dev / feature-xxx
- 测试环境：真实环境（页面 8080 + API 8765 + 真实 LLM）或 本地单测

### 自动化测试
| 项 | 命令 | 结果 |
|---|---|---|
| pytest | `pytest -q` | ✅ 172 passed |
| ruff | `ruff check src` | ✅ All checks passed |
| mypy | `mypy src` | ✅ 0 error |
| JS 语法 | `node --check *.js` | ✅ 全部通过 |

### 真实环境验收（前端改动必做）
- Playwright 截图：`tests/e2e/screenshots/xxx.png`
- pageerror：0 ✅ / console error：0 ✅ / 4xx：0 ✅
- 关键交互验证：
  - [ ] 步骤描述 + 结果
  - [ ] ...

### 结论
✅ 全部通过 / ⚠️ 部分待修 / ❌ 未通过（说明）
```

## 五、存档要求

1. **每个模块一个文件**：`docs/modules/<module>.md`（模板见 `docs/modules/_template.md`）
2. **索引维护**：`docs/modules/README.md` 登记每个模块的最新状态（✅ 通过 / 🚧 开发中 / ⚠️ 待修）
3. **变更历史**：模块文件底部追加「变更记录」，最新在上
4. **每次功能迭代都要更新对应模块文件**，不新建重复文件
5. 截图统一放 `tests/e2e/screenshots/`，文档里引用相对路径

---

## 六、与开发复盘规范的关系

- §4.10 强制规范：**任何模块开发，先建清单、后填结果，缺一不可**
- 验收清单（playbook §5）全绿才允许 PR 合入 main
- 模块文档就是开发的"留痕"，便于追溯"每个功能当时怎么验证的"
